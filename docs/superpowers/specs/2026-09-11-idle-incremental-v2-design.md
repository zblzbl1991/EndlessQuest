## 二、V2 总体结构：四层循环

```
微循环（30秒~5分钟）  修炼 → 打怪 → 掉装备 → 战力提升
小循环（30分钟~3小时）突破境界 → 解锁系统/建筑 Milestone → 新资源 → 效率跃升
中循环（1~3天）       渡劫 → 飞升(Prestige①) → 道韵 → 飞升树 → 永久成长
大循环（1~4周）       仙界 → 证道(Prestige②) → 大道本源 → 世界重构
```

境界即主进度条：**每个境界必须改变玩法，而不只是属性 ×1.8。**

| 炼气 | 基础挂机：灵田/灵矿/聚灵阵生产链、手动突破 |
| 筑基 | 秘境（已有）+ 装备自动最优 + 自动出售凡品 |
| 金丹 | 炼丹自动化 + 灵宠（已有）+ 祝福 Build雏形 |

| 化神 | 大境界自动突破（可设保留确认）+ 洞天福地 |
| 炼虚 | 飞升预览面板：道韵模拟器、飞升条件清单 |

| 真仙~道祖 | 证道(Prestige②) → 大道本源树 → 超脱 |

## 三、数值底座：BigNumber 策略（P0）

### 3.1 决策

V2 引入 **break_eternity.js**（支持到 10^^1e308，API 与 break_infinity 兼容，社区活跃）。不做自研 Decimal——增量游戏的数值边界情况（极小速率、0 的幂、Infinity 序列化）自己封一定会踩坑。

落地方式：**新建 `src/utils/Decimal.ts` 统一封装**，规则：

1. 全部资源、修为、战力、成本字段在**存档序列化时**存 `{m: mantissa, e: exponent}`（break_eternity 原生 `toJSON/fromJSON`），兼容层提供 `fromLegacyNumber(n)` 迁移旧档。
2. 引擎层（CultivationEngine/ProductionSystem/tickSlice）只接受/返回 `Decimal`；UI 层通过统一格式化函数 `formatNumber()` 显示（`1.23e145` / 中文单位 `1.23垓` 双模式，设置里切换）。
3. 迁移顺序：先**修为 + 建筑成本**两条曲线（溢出最快），资源四件套第二批，战斗数值最后（战斗可以继续用 `number`，只要攻防比在引擎内换算成对数比较）。
4. 溢出防护：保留现有 `normalizeFiniteNumber`（`SaveSystem.ts:148-159`）思路，扩展为 `normalizeDecimal`，读档时把 NaN/Infinity 修回默认值。

### 3.2 为什么现在就要做

现有全周目修为总量 ≈ 214 万（`realms.ts` 各段求和），普通 number 远不会溢出——**但 V2 境界曲线到 10^100、道韵树倍率乘上去之后，第三世就会撞 `1e308`**。BigNumber 是所有后续公式的前提，必须最先落地。

```
灵气 ──→ 修为 ──→ 境界 ──→ 战力 ──→ 高级区域 ──→ 高级资源 ──→ 灵气效率
         ↑丹药加速  ↑功法转化率        ↑秘境/远征
```

| 资源 | 定位 | 获取 | 消耗 | V2 变化 |
|---|---|---|---|---|
| 灵气 | 最底层生产资源 | 聚灵阵（Generator） | 弟子修炼 2/秒/人（保留现有机制）、建筑运转 | 成为前期核心瓶颈；上限随聚灵阵 Milestone 指数放宽 |
| 修为 | 境界进度 | 修炼（灵气驱动） | 突破清零 | 曲线改指数（见 §5） |
| 灵石 | 通用货币 | 灵矿 + 税收 + 变卖 | 建筑/招募/突破/坊市 | 取消 140 万硬上限，改 `cap = 主殿等级^2 × 1e4 × 飞升加成` 软上限 + Milestone 放宽 |
| 天材地宝 | 高阶材料（现有 herb/ore 升级 + 新增妖丹/灵晶） | 灵田/灵矿/秘境 | 炼丹/炼器/高阶突破/洞天 | 分阶：下品→中品→上品→极品→仙品，秘境层深决定品阶 |

## 五、境界数值公式 V2（P0）

### 5.1 境界表

凡界 9 境 + 仙界 4 境。大境界满阶修为需求 `RealmCost(i) = 10^EXP[i]`：

| i | 境界 | EXP | RealmCost | 属性倍率 | 首次到达目标耗时* |
|---|---|---|---|---|---|
| 0 | 炼气 | 2 | 1e2 | ×8 | 10 分钟 |
| 1 | 筑基 | 4 | 1e4 | ×8 | 30 分钟 |
| 2 | 金丹 | 6 | 1e6 | ×8 | 1.5 小时 |
| 3 | 元婴 | 9 | 1e9 | ×8 | 4 小时 |
| 4 | 化神 | 13 | 1e13 | ×8 | 8 小时 |
| 5 | 炼虚 | 18 | 1e18 | ×8 | 1 天 |
| 6 | 合体 | 24 | 1e24 | ×8 | 1.5 天 |
| 7 | 大乘 | 31 | 1e31 | ×8 | 2 天 |
| 8 | 渡劫 | 40 | 1e40 | ×8 | 3 天（→首次飞升） |
| 9 | 真仙 | 50 | 1e50 | ×10 | 仙界层，1 周 |
| 10 | 金仙 | 65 | 1e65 | ×10 | 仙界层 |
| 11 | 大罗 | 80 | 1e80 | ×10 | 仙界层 |
| 12 | 道祖 | 100 | 1e100 | ×10 | 大循环终点（证道解锁） |

\* 首世目标节奏，含离线；详细见 §12 前 7 天节奏表。属性倍率从固定 ×1.8 改为 **×8/大境界（仙界 ×10）**——战力必须指数增长才能打上指数增长的敌人（秘境敌人同步 ×8 缩放，相对难度不变，绝对数字爆炸）。

### 5.2 小境界

每大境界 4 小阶段，需求 = `RealmCost(i) × [0.05, 0.15, 0.30, 0.50]`（累计 50% 处小境界全过，大境界突破吃掉后半程并清零）。小境界突破成功率固定 90%（去掉现有引擎层二次 roll，见 B3/B5 顺手清理），失败保留 100% 修为只耗资源——**前期不允许有惩罚性挫败，风险留给大境界渡劫**。

### 5.3 速率公式（增量游戏的核心平衡律）

增量游戏的铁律：**修为速率的增长必须压得住成本的增长，否则后期变成纯墙壁。**

```
修为速率 = BASE(5/秒)
  × 灵根系数 (root/10)^0.85                    // 保留
  × 悟性系数 (1 + (comp-10)×0.015)             // 保留
  × 境界自速倍率 RealmSpeed(i) = 3^i           // 新增：境界本身 ×3/层
  × 功法乘积                                   // 保留乘法叠加
  × 建筑加成 (藏经阁/聚灵阵 Milestone)          // 新增
  × 道韵树倍率                                 // 新增
  × 飞升次数全局倍率 (1 + ascCount × 0.5)      // 新增
  × 灵气供给比 spiritScale                     // 保留（灵气瓶颈）
```

校准律：`RealmSpeed(i) × 其他倍率增长率 ≥ RealmCost(i+1)/RealmCost(i) 的对数增速`。具体地，EXP 差 [2,2,3,4,5,6,7,9] 对应成本增速 10^2~10^9，而 `3^i` 单项就是 3~6561 倍，叠加功法/道韵树后每境界净耗时按 §5.1 表递增——**前期境界越来越快，中后期缓慢变慢，飞升后全局倍率把整条曲线压缩**。这正是"第二世 ×3 倍速、第十世 ×100 倍速"的实现方式。

现有 `REALM_CULTIVATION_MULT = [1.0, 0.9, 0.8, 0.7, 0.6, 0.5]`（境界越高越慢）**废弃**——它与指数曲线矛盾，被 `3^i` 与成本曲线的差值取代。

### 5.4 突破与渡劫

- 大境界突破保留五档结果梯度（great_success 10% / success 50% / blocked 20% / injured 15% / fallen 5%），但 **fallen 仅在渡劫(→8)及以后存在**，凡界前期 0%。
- 渡劫改为**每个大境界都有**，失败率 = `0.15 + EXP[i]×0.004 − 灵根×0.005 − 悟性×0.003 − 道韵树减劫节点`，修好 B3 的死数据问题。
- 突破消耗：灵石 = `RealmCost(i) × 0.02`（指数联动，天然解决 B1 的 150 万 > 140 万断点），材料消耗用天材地宝品阶挂钩。

## 六、建筑 Generator V2 + Milestone（P1）

### 6.1 成本公式

现有幂曲线 `200 × (lv+1)^1.7`（3 级 ≈ ×3.3）偏传统 RPG。改为标准增量成本：

```
cost(level→level+1) = baseCost × growth^level × 飞升减负(可选节点)
```

| 建筑 | 产出/效果 | baseCost(灵石) | growth | Milestone（新机制，每档永久生效） |
|---|---|---|---|---|
| 聚灵阵 | 灵气 `(3+2lv)/秒/座` → V2 `3 × 1.10^lv` | 100 | 1.15 | Lv10 灵气×2；Lv25 解锁自动升级；Lv50 灵气×3；Lv100 灵脉共鸣（灵田灵矿产量+50%）；Lv250 每级+1% 修炼速度；Lv500 解锁自动购买低阶建筑 |
| 灵田 | 药草 `3 × 1.08^lv`/秒/座 | 150 | 1.16 | Lv10 药草×2；Lv25 解锁自动炼丹；Lv50 掉落品质+1 档；Lv100 药园自动化（自动补种/收获） |
| 灵矿 | 灵石 `2 × 1.09^lv` + 矿材/秒/座 | 200 | 1.17 | Lv10 灵石×2；Lv25 解锁自动出售废装；Lv50 矿材×3；Lv100 解锁灵石上限 Milestone 放宽 |
| 藏经阁 | 修炼效率 `+2%/级`（乘法，软上限 +200%） | 400 | 1.20 | Lv25 参悟心得：功法熟练度获取×2；Lv50 解锁功法融合；Lv100 每已学功法 全局+2% |
| 炼丹房 | 自动炼丹吞吐 | 800 | 1.22 | Lv10 丹效×1.5；Lv25 丹方自动切换；Lv50 炼丹暴击（双倍产出 10%）；Lv100 副产品：每炉附带 1 极品材料 |
| 炼器阁 | 自动炼器吞吐 | 800 | 1.22 | Lv10 成功率+15%；Lv25 自动强化；Lv50 强化保底（失败不掉级）；Lv100 神器锻造解锁 |
| 御兽峰 | 灵宠经验/捕获率 | 1200 | 1.25 | Lv10 捕获率+20%；Lv25 宠物栏+2；Lv50 宠物继承；Lv100 灵宠协战（第二只参战） |
| 主殿 | 位阶/地块上限/税收 | — | 境界解锁 | 等级上限 = 境界 index × 2（炼气 Lv2 → 渡劫 Lv16），保留"主殿管扩张"的角色 |

- 等级上限从 6~10 解除为**无上限**（成本指数自然封顶）。
- 扩建公式保留 `(count+1)^1.6`，座数上限改由主殿等级 + Milestone 双驱动。
- 现有协同系统（药脉流转/矿火淬炼等 5 条，`buildings.ts:326-387`）保留，作为"建筑布局策略"层。
- 现有建筑生态/专长/指派（每建筑 3 人）保留——弟子指派是"挂机修仙"特色，与 Generator 并存：**建筑产基数，弟子加成数，Milestone 产倍率**。

### 6.2 Milestone 释放节奏

每建筑前 3 档 Milestone 对应小循环（30 分钟~3 小时），后面几档跨境界释放。**Milestone 表就是 V2 的"内容释放阀门"**——境界解锁管"新玩法出现"，Milestone 管"旧玩法变强变自动"。

## 七、飞升 Prestige V2（P0）

### 7.1 重置/保留清单

**重置**：境界、修为、灵石/灵气/材料（天材地宝按品阶保留 1 件做纪念/图鉴）、普通建筑等级、普通装备（转为道韵加成参考）、秘境层数进度、弟子（保留 1 名，V2 改为保留**最高境界**弟子转为"护法"，而不是随机凡品）。

**保留**：图鉴（怪物/装备/功法）、档案里程碑（19 种）、飞升次数、道韵 + 飞升树、隐藏功法/秘境解锁、远征模板槽、宗门原型偏好（作为"宗门记忆"）。

### 7.2 道韵公式

```
道韵 = floor( (本世最高修为)^0.1 / 1000 × (1 + 0.3 × 最高境界index) × (1 + 0.25 × 历史飞升次数) )
```

校准目标（配合 §5.1 曲线用模拟脚本 `scripts/` 调参）：

| 飞升 | 首次到达 | 预期道韵 |
|---|---|---|
| 第 1 次 | 渡劫 1e40 | ≈ 12 |
| 第 2 次 | 渡劫+更快 | ≈ 85 |
| 第 3 次 | 真仙 1e50 | ≈ 630 |
| 第 5 次 | 金仙 1e65 | ≈ 4 万 |
| 第 10 次 | 道祖 1e100 | ≈ 3M+ |

## 十二、主循环技术方案：setInterval 的替代（P0，直接回答）

### 12.1 现方案（setInterval 1000ms）的真实问题

读了 `IdleEngine.ts` 全文，现有架构**方向是对的**：tick 不假设"过了 1 秒"，而是用 `Date.now()` 差值算 delta（`tick(): 61-70`），隐藏暂停 + 回来补算（`handleVisibility: 40-59`）。这是 delta-time 模型，比裸 setInterval 数次数强得多。但仍有四个问题：

1. **前台粒度粗**：1 秒 1 tick + `deltaSec >= 0.5` 才生效（`tick():66`），UI 数字每秒只跳一次，速率显示滞后；单 tick 增量截断 10s，若主线程卡顿 >10s 就静默丢时间。
2. **setInterval 被浏览器节流**：后台标签页 Chrome 会把 timer 降到 ≥1 次/分（开启节能后前台也可能被 Intensive Throttling 降到 1 次/分）。虽然现在靠 `document.hidden` 主动 clearInterval 规避了"半死不活"状态，但**前台高负载时 setInterval 同样会漂移堆积**，只是被 delta 模型掩盖了。
3. **前台与离线两套结算逻辑**：活动态走逐秒 tick（事件、队列、随机数都跑），离线走单次大 tick + 闭式解（`calcOfflineProduction`），两条路径的结果有偏差（离线随机事件只 roll 1 次就是例证，B7）。玩家会感知"挂机收益和在线不一样"。
4. **暂停语义靠 callback 里 return**（`App.tsx:120-122`），时间戳仍在推进，暂停期间的时间依赖"回来补算时 lastTickTime 恰好被跳过"这类隐式约定，容易在重构中破坏。

### 12.2 V2 方案：单一 simulate 函数 + 三个入口

**原则：模拟与调度分离。把 `tickSlice.tickAll` 精炼为一个纯函数 `simulate(state, deltaSec, mode)`，前台、后台恢复、离线读档三个入口全部调它，只是 delta 不同、路径不同。**

```
入口A 前台：requestAnimationFrame 驱动
  rAF 每帧算 frameDelta（上限 250ms 防卡顿跳变）
  → 固定步长累加器 fixedStep = 200ms：while(acc ≥ step) { simulate(step); acc -= step }
  → 渲染每帧做（数字平滑插值，可以显示 0.2 秒粒度的增长）
  rAF 在页签隐藏时自动停发 → 天然"暂停"，无需手动 clearInterval

入口B 可见性恢复/窗口聚焦：catch-up
  elapsed = now - lastSimTime（用独立时间戳，不依赖 rAF）
  → elapsed ≤ 120s：按固定步长循环补 simulate
  → elapsed > 120s：走闭式解快路径（见下）

入口C 读档离线：offline catch-up
  同入口B，上限 24h（道韵树可扩），产出闭关报告
```

**大 delta 的闭式解快路径**（>2 分钟不再逐秒模拟）：
- 资源/修为：`产出 = Σ 速率 × 时间`，速率取起止两端的均值修正（或分段：按境界变化点切段积分）；上限截断直接对积分结果 clamp。
- 生产队列：保留现有 `calcOfflineProduction` 闭式解（它已经是正确的做法）。
- 随机事件：期望次数 `λ = rate × duration`，泊松/二项抽样决定发生几次，再逐次 roll 结果——离线 8 小时和在线 8 小时统计分布一致（修 B7）。
- 战斗/秘境：按"每层平均耗时 × 层数"估算推进层数，逐层结算奖励（层数多时封顶 100 层防止卡顿）。

### 12.3 逐条回答"有没有更好的方法"

| 问题 | 答案 |
|---|---|
| 要不要继续 setInterval？ | 前台不要。换 **requestAnimationFrame + 固定步长累加器**（模拟步长 200ms，帧率无关、防漂移、隐藏自动停）。interval 只保留一个 30s 心跳做兜底（防止某些浏览器 rAF 异常冻结），心跳内容也是调 catch-up 路径。 |
| 要不要 Web Worker？ | 现阶段不要。当前每 tick 计算量小（纯 number 运算 + 少量弟子循环），主线程足够；V2 引入 BigNumber 且弟子/建筑上千后，把 `simulate` 移入 Worker（SharedArrayBuffer 或 postMessage 状态快照）再考虑，架构上 `simulate` 纯函数化后随时可移。 |
| 后台标签页要不要跑？ | 不要真跑（无法对抗节流，也没必要）。隐藏→恢复之间用 catch-up 补算，体验等价。这正是现有 `handleVisibility` 的思路，V2 只是把补算粒度从"一个 24h 大 tick"改为"分段积分 + 统计抽样"。 |
| 暂停怎么处理？ | `simulate` 接收显式 delta，暂停时不产生 delta（不再依赖 callback 里 return 的隐式语义），存档记 `pausedAt`，恢复时从 `pausedAt` 重算。 |
| 存档频率？ | write-through 每秒全量改 **dirty-flag + 5 秒防抖**（`startAutoSave.ts`），`visibilitychange`/`beforeunload` 立即 flush（保留现有行为）。V2 资源改 Decimal 后序列化体积变大，这一条必须同步做。 |

### 12.4 迁移步骤（不动 gameplay 的前提下可独立合入）

1. 抽 `simulate(state, deltaSec)` 纯函数（现 `tickSlice.tickAll` 改造，行为不变，加回归测试：同 delta 多次模拟结果确定性）。
2. 新 `GameLoop` 类替换 `IdleEngine`：rAF + 累加器 + 三入口，`TICK_INTERVAL_MS` 语义废弃。
3. OfflineReport 改为统一 catch-up 的产出（离线/在线同路径）。
4. 存档节流改造。
